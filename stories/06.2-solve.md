# Story 06.2 — General dense Tensor solve: LAPACK fast path and generic QR fallback

## Dependencies

- **Story 06 — Tensor index symmetry & backend seam.** Tensor owns labels,
  shape validation, output shaping, and executor choice; backend kernels see
  only dense buffers and extents.
- **Story 06.1 — General Tensor axis permutation and transpose.** Callers use
  `permute_axes` explicitly when their operands are not in the solve layout
  required below. This story must not hide data-moving permutations.
- `include/multiprecision.hpp`'s `numerics::FloatingPoint` taxonomy.
- Existing CMake LAPACK discovery/linkage (`LAPACK::LAPACK`).
- The warning-level feature in `include/types.hpp`:
  `warn_if(required_level, message)`.

## Motivation

GF2 needs to solve the AO Dyson equation at every Matsubara point,

```text
A(iω_n) G(iω_n) = I,
```

without constructing `A(iω_n)⁻¹`. A rank-two, `double`-only wrapper around
LAPACK is insufficient for this codebase: Tensor data may contain arbitrary
leading/trailing physics dimensions, the solve must follow the same explicit
axis-order discipline as `gemm`, and numerical tests/use cases may use the
multiprecision scalar types already recognized by `multiprecision.hpp`.

This story adds one general Tensor solve primitive. It has two numerical
implementations:

1. **Host LAPACK fast path:** `dgesv` for `double` and `zgesv` for
   `std::complex<double>`.
2. **Generic host fallback:** a hand-coded, column-pivoted Householder QR solve
   for every other `numerics::FloatingPoint` scalar, including `float`, `long
   double`, Boost real multiprecision, and supported complex FloatingPoint
   types. It is the correctness/portability fallback, not an attempt to compete
   with tuned LAPACK.

The public operation is out-of-place like `gemm`: it accepts arbitrary-rank
coefficient and RHS Tensors, validates the explicitly supplied solve axes,
broadcasts over all remaining dimensions according to the same outer-product
rule as `gemm`, and shapes/writes an output Tensor.

## Resolved API and layout decisions

The following choices are deliberate; they remove ambiguities that matter for
both Tensor labels and batched solves.

### Solve-axis descriptor

A linear map has separate domain (column) and codomain (row) axes. One label
is not sufficient to identify both, especially now that labels can be repeated
within an advisory symmetry family. The API therefore receives an **ordered
set of row/column axis pairs**:

```cpp
struct SolveAxis {
  TensorDimLabel row;      // codomain axis: A row, B row
  TensorDimLabel column;   // domain/output axis: A column, X row
};

// X is shaped/written just as Z is by gemm.
template <numerics::FloatingPoint TA,
          numerics::FloatingPoint TB,
          numerics::FloatingPoint TX,
          typename Exec>
void solve(const Tensor<TA, Exec>& A,
           const Tensor<TB, Exec>& B,
                 Tensor<TX, Exec>& X,
           std::span<const SolveAxis> axes);
```

Provide `std::vector` and `std::initializer_list` convenience overloads.
Arithmetic is performed in `TX`, as `gemm` performs arithmetic in its output
scalar type. `TA` and `TB` must be losslessly/explicitly convertible to `TX`
under the project's selected conversion policy; this story may initially
require `std::convertible_to<TA, TX>` and `std::convertible_to<TB, TX>`.

`axes` is the requested “set of dimensions to solve over.” Its order is
semantically significant: it is fastest-to-slowest within the flattened matrix
row and column multi-indices. An empty set is invalid.

A convenient one-axis AO call is:

```cpp
solve(A, B, X, { SolveAxis{TensorDimLabel("ao_row"),
                           TensorDimLabel("ao_col")} });
```

For a multi-index linear space, e.g. `(spin, ao)`, the caller supplies two
ordered pairs. This flattens the Cartesian product of the row axes and the
Cartesian product of the column axes into one dense matrix. No reshape API is
introduced.

### Required operand ordering — intentionally analogous to `gemm`

For `p = axes.size()`, dimensions are always fastest-to-slowest. A valid
coefficient Tensor must be laid out as

```text
A: [ row_0, ..., row_(p-1), column_0, ..., column_(p-1), A_free... ]
```

and a valid RHS Tensor as

```text
B: [ row_0, ..., row_(p-1), B_free... ].
```

The first `p` dimensions of `A` must have exactly the `row` labels from
`axes`, in order. Its next `p` dimensions must have exactly the corresponding
`column` labels, in order. The first `p` dimensions of `B` must have the same
ordered `row` labels. `A` therefore has at least `2p` axes and `B` at least
`p` axes.

For every axis pair, the `A` row, `A` column, and `B` row extents must agree.
This story solves square systems. Pairwise equality, rather than merely equal
products, prevents a silent and physically meaningless solve between differently
shaped multi-index spaces.

This is the solve equivalent of `gemm`'s requirements that X's contracted axis
be last/slowest and Y's contracted axis first/fastest. A label occurring in an
incorrect position is a hard `std::invalid_argument`; the implementation must
not search for it, infer a permutation, or transpose behind the caller's back.
For a valid but differently ordered Tensor, the caller explicitly applies
Story 06.1 `permute_axes` first.

Validation is position-based. It must never rely on `label_index`, because that
returns only the first member of a duplicate symmetric-family label. Equal
labels in the row and column positions are permitted if the explicit positions
match the requested layout, although distinct `ao_row`/`ao_col` labels are
recommended for derived non-symmetric matrix quantities such as a fixed-
frequency Matsubara Green's function.

### Broadcasting rule for all other dimensions

Let

```text
N    = product(row dimensions) = product(column dimensions)
M_A  = product(A_free dimensions)
NRHS = product(B_free dimensions).
```

The result is shaped exactly in the free-dimension style of `gemm`:

```text
X: [ column_0, ..., column_(p-1), A_free..., B_free... ].
```

For each coordinate `a` in `A_free` and each coordinate `b` in `B_free`, solve

```text
A[:,:,a] X[:,a,b] = B[:,b].
```

Thus every coefficient-matrix block broadcasts across every RHS-free block,
and every RHS block is solved against every coefficient-free block. This is the
same Cartesian-product/outer-product meaning that `gemm` gives its surviving
free axes; it is deliberately **not** NumPy-style matching-name batch
broadcasting. Repeated free labels can therefore make the output Tensor invalid
under the existing Tensor duplicate-label rules, just as with `gemm`; normal
`prepare_output` validation must report that rather than silently merging axes.

`B_free` is interpreted as a flattened set of RHS columns for a fixed
coefficient block. This makes a matrix RHS, a vector RHS, and arbitrary
additional physics dimensions one operation without a separate RHS-rank API.

### Mutation semantics

The public `solve(A, B, X, axes)` does not modify `A` or `B`; it shapes or
validates `X` using `Tensor::prepare_output`, just as `gemm` does.

For each `A_free` block, it creates contiguous `TX` working buffers:

```text
coefficient: N × N
rhs:         N × NRHS
```

then calls an internal/backend **in-place** solve which may overwrite both
buffers. The completed RHS work matrix is scattered into the strided output
layout `[column, A_free, B_free]`. This copy/scatter is intentional: while the
coefficient block is contiguous under the required layout, the complete RHS
set for one `A_free` coordinate is not generally contiguous in the output.
The story must not reinterpret a strided Tensor slice as a LAPACK matrix.

## Numerical backend contract

Extend `TensorBackend<T, Executor::Host>` with an internal raw operation:

```cpp
static void solve_in_place(TensorBuffer<T, Executor::Host>& coefficient,
                           size_t n,
                           TensorBuffer<T, Executor::Host>& rhs,
                           size_t nrhs);
```

Preconditions:

- `coefficient.size() == n * n` and `rhs.size() == n * nrhs`;
- `n > 0`, `nrhs > 0`, and the buffers are writable, dense, host-resident, and
  non-aliasing;
- `T` satisfies `numerics::FloatingPoint`;
- `n` and `nrhs` fit the relevant LAPACK integer type when the LAPACK path is
  selected.

The raw backend sees only flat buffers and sizes. It receives no labels,
`SymGroup`, axis descriptors, HDF5 objects, or GF2/Matsubara information.
Tensor-level validation and batch/scatter logic remain in the frontend.

Add the solve operation to the backend-op concept only if that concept can
express the scalar constraints cleanly; otherwise define a focused solve
concept. Existing backends must not accidentally claim support for it merely
because they support `gemm`.

## LAPACK path

For exactly `double` and `std::complex<double>`, the host backend delegates to
the configured LAPACK ABI:

```text
dgesv  — double
zgesv  — std::complex<double>
```

The required Tensor row-fast storage has offset `row + N * column`, which is
LAPACK's column-major layout. The contiguous work buffers therefore need no
transpose or element reordering.

Bind the routines in one source/implementation location with checked conversion
from `size_t` to the configured LAPACK integer ABI. Do not silently narrow
large dimensions. LAPACK overwrites the coefficient with pivoted LU factors and
the RHS with the solution, which is compatible with the raw in-place contract.

For `info < 0`, throw an actionable programming/argument error naming the
routine and offending argument. For `info > 0`, the matrix is singular:

1. call `warn_if(1, ...)` with the routine and singular pivot index; then
2. throw `std::runtime_error`.

Default verbosity remains silent, as established by `types.hpp`; the exception
still occurs regardless of verbosity. A warning supplements failure and must
not turn a singular solve into a fabricated solution.

## Generic QR fallback

Every `numerics::FloatingPoint` output type other than the two LAPACK fast-path
types uses a hand-coded **Householder QR factorization with column pivoting**.
Column pivoting is required: unpivoted QR can solve a well-conditioned square
system but gives weak rank detection for nearly dependent columns. The fallback
must work for the scalar taxonomy already accepted by `multiprecision.hpp`, not
only native real `float`/`long double`.

For each dense work problem it must:

1. factor `A P = Q R` with Householder reflectors and column pivoting;
2. apply `Qᴴ` to all `NRHS` columns in the same factorization pass;
3. determine numerical rank from the diagonal of `R`;
4. back-substitute the triangular system for the permuted unknowns; and
5. undo the column permutation to write `X`.

The implementation must add/centralize minimal scalar helpers usable for native
and Boost real/complex values: real-component type, conjugation, absolute
magnitude, square root, and machine epsilon. Use ADL-friendly `abs`, `sqrt`,
and conjugation helpers rather than assuming `std::complex` only. If a claimed
`FloatingPoint` type cannot supply those operations, reject it with a clear
compile-time diagnostic and either correct `multiprecision.hpp`'s concept or
narrow the solve concept; do not allow a template-instantiation avalanche.

### Rank threshold and singularity behavior

For a square factorization, define a documented scale-aware rank threshold,
for example

```text
tol = c * epsilon(real_scalar) * max(N, 1) * max_column_norm(A),
```

where `c` is a small documented constant. Treat `abs(R_kk) <= tol` as
numerically singular/rank-deficient. The exact scale formula may be refined,
but it must be shared by real and complex fallback paths and tested with both
ordinary and multiprecision scalars.

On a rank-deficient fallback solve:

1. call `warn_if(1, ...)` identifying the QR fallback, detected rank/pivot,
   and threshold; then
2. throw `std::runtime_error`.

This story does **not** return a least-squares, minimum-norm, pseudoinverse, or
partially solved result. Those are valid future APIs but have different
mathematical contracts. The caller receives no successful output from a
singular block. If the Tensor frontend is solving many broadcast blocks, it
must include the failing `A_free` coordinate in the thrown context.

The fallback is required even when LAPACK is present: it is how Tensor solve
remains usable with multiprecision types and scalar types for which this build's
LAPACK ABI has no matching routine.

## Frontend algorithm

`solve(A, B, X, axes)` performs these steps:

1. Validate nonempty `axes`, executor support, ranks, exact axis label order,
   and pairwise row/column/RHS extents.
2. Form output dimensions from A's column block, then A's free dimensions,
   then B's free dimensions; call `X.prepare_output(output_dims, "solve")`.
3. Compute `N`, `M_A`, and `NRHS` with checked multiplication/overflow errors.
4. For each linear `A_free` block:
   - convert/copy the contiguous `N × N` coefficient block into `TX` work
     storage;
   - convert/copy all `B` values into contiguous `N × NRHS` RHS work storage;
   - call `TensorBackend<TX, Exec>::solve_in_place`;
   - on failure, rethrow with the `A_free` coordinate/index and requested axis
     names; singularity warnings have already been emitted by the backend;
   - scatter the solved work RHS into the `[column, A_free, B_free]` output.

For the common GF2 use case, `A_free` is empty and `B` is an identity matrix,
so the public operation makes one complex solve with `NRHS == N`. GF2 must use
this primitive rather than implementing a local frequency-slice solver.

## Error and warning policy

- Wrong label order, missing solve axis, non-square paired dimensions,
  rank/shape mismatch, output-shape mismatch, unsupported executor, and
  checked-size overflow: `std::invalid_argument` (or the project's documented
  range exception for impossible dimensions), with axes/positions named.
- LAPACK illegal argument: logic/invalid-argument error naming routine and
  argument.
- LAPACK singular pivot or QR numerical rank deficiency: warning through
  `warn_if(1, ...)`, then `std::runtime_error`.
- No warning is emitted for a correctly solved ill-conditioned-but-full-rank
  system. Condition-number estimation/refinement is out of scope.
- No partial or best-effort `X` is exposed after a failed block solve. Existing
  `X` allocation may exist internally, but callers must treat the operation as
  failed.

## Tests

Add a dedicated solve test function to the existing in-process `-t` suite.

### 1. Rank-two real LAPACK solve with multiple RHS

Use `double` `A[row, column]` and `B[row, rhs]`, solve into
`X[column, rhs]`, and compare against a hand/reference solution and residual.
Verify input `A`/`B` are unchanged, while the raw backend's work buffers are
allowed to change.

### 2. Complex LAPACK solve

Use a non-Hermitian `std::complex<double>` matrix and several RHS columns.
Verify all complex values and the residual. This is the direct primitive used
by the AO Matsubara GF2 solve.

### 3. Multi-axis solve space

Construct a coefficient Tensor with solve blocks

```text
[row_spin, row_ao, column_spin, column_ao]
```

and RHS with `[row_spin, row_ao, rhs]`. Verify flattening order, result shape
`[column_spin, column_ao, rhs]`, and every coordinate against a manually
flattened reference. This catches reversed multi-index order.

### 4. Free-dimension broadcasting

Use

```text
A: [row, column, a_free]
B: [row, b_free_0, b_free_1]
X: [column, a_free, b_free_0, b_free_1].
```

Fill each `A_free` matrix and each RHS block differently. Verify every
`(a_free, b_free_0, b_free_1)` solve independently. Confirm the output order
is A-free then B-free, exactly as `gemm` orders surviving free axes.

### 5. Ordering and validation regressions

Verify hard errors for:

- a requested row/column label in the wrong position;
- row/column axes swapped;
- a valid differently ordered input that succeeds only after explicit
  `permute_axes`;
- missing/empty axis sets;
- unequal paired row/column/RHS extents;
- insufficient rank;
- output Tensor with incompatible preallocated dimensions;
- invalid output duplicate labels under normal `prepare_output` validation;
- unsupported executor and checked product/LAPACK-integer overflow where
  practicable.

Include a duplicate-label symmetric-family fixture to prove validation uses
physical positions rather than `label_index`.

### 6. QR fallback coverage

- `float` or `long double`: verify the generic QR fallback matches a reference
  residual/solution and does not route to LAPACK.
- `numerics::float50`: solve a small real system with a much tighter residual
  than double permits, proving the fallback compiles and uses multiprecision
  arithmetic.
- A supported complex non-LAPACK scalar (such as `std::complex<long double>`;
  Boost complex too when available in the configured multiprecision setup):
  verify conjugate-Householder QR and residual correctness.
- A rank-deficient matrix for both LAPACK and QR paths: set verbosity to `1`,
  capture/observe the warning hook if the test framework supports it, and verify
  an exception rather than a fabricated solution. Restore global verbosity
  afterward.

### 7. Regression

All existing Tensor, symmetry, permutation, `gemm`, Fourier,
inverse-Fourier, input-loading, and GF2-linkage tests continue to pass.

## Definition of done

- `solve(A, B, X, axes)` accepts arbitrary-rank host Tensors and an ordered set
  of solve-axis pairs.
- It rejects incorrectly ordered dimensions just as `gemm` rejects an
  incorrectly placed contracted axis; no hidden transpose occurs.
- It produces `[column axes, A free axes, B free axes]` and performs the
  documented outer-product broadcast across all free dimensions.
- `double` and `std::complex<double>` use checked LAPACK `dgesv`/`zgesv`.
- Every other supported `FloatingPoint` type uses the tested hand-coded
  column-pivoted Householder QR fallback.
- Singular/rank-deficient systems issue a verbosity-level-1 warning and then
  fail; no inverse, pseudoinverse, or partial solution is returned.
- Backend kernels remain unaware of labels, symmetry, Tensor rank, and physics.
- The complete repository test suite passes.
