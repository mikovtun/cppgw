# Story 05.1 — Input-framework cleanup: per-calculation requirement sets and dataset definitions

> **Brief (original):**
>
> This story is to fix some straggling API issues the previous story 05 about input
> loading created. For one, this code will be supporting multiple calculations beyond
> just GF2, and each of those calculations have different keywords that are required
> and optional. However, the KeywordDefinition class has a calculation-specific bool:
> `required_for_gf2`. This isn't an extensible solution, because it's a hardcoded
> object just for GF2. The input datasets should be specified:
> * in a single place
> * as strings ("DENSITY_MATRIX") alongside DimLabels specifying axis labels/dims and
>   Symmetries
>
> Callers that request the datasets later in the code can refer to them simply by
> their strings and receive the corresponding Tensor. The input datasets should be
> validated upon entry: ensuring the input has the expected rank and symmetry (check
> the elements of the Tensors for the correct Symmetry). Each calculation has a set of
> required and optional datasets and parameters. There should be an abstraction of
> required/optional sets of datasets/parameters that can be reused for different
> calculations.

## Status, dependencies, and scope boundary

This is an **API-cleanup story** on top of the landed input framework (Story 05) and
the GF2 requirement set extended by Story 07.1 (five datasets + three parameters). It
removes the GF2-specific hardcoding from the *generic* input machinery and moves the
GF2 dataset layout/extent/symmetry knowledge into the framework's single
definitions-registry, in the form the brief requires.

It **adds no calculation**, changes **no parser grammar**, adds **no new input
keyword or value kind**, changes **no GF2 numerics**, and keeps
`Gf2Input`, `make_gf2_initial_guess`, and every existing error message
(needle-compatible) intact. It is deliberately sized for one pass: two files
touched hard (`include/input.hpp`, `src/input.cpp`), two touched lightly
(`include/gf2.hpp` doc comments, `src/gf2.cpp` `require_gf2` body), tests
extended in place. No new files, no CMake change.

### Dependencies

- **Story 05 — Input parsing & data loading.** Everything here rewrites or
  supersedes pieces of `include/input.hpp` / `src/input.cpp` (the
  `required_for_gf2` registry flag, the calc-resolution and requirement
  checks, the dataset loading currently living in `src/gf2.cpp`).
- **Story 06 — Tensor index symmetry.** Provides the `SymKind` enum
  (`Symmetric`/`Hermitian`/`Antisymmetric`) and the `Hermitian()`/`Symmetric()`
  factories used to declare the bindings on the loaded tensors, plus the
  label/symmetry invariant (`Tensor::validate_dims_and_symmetry`) that
  `Tensor` construction itself enforces.
- **Story 07.1.** Fixed the GF2 requirement set this story must reproduce
  exactly: datasets `HCORE`, `MO_COEFF`, `ERI3`, `OVERLAP`,
  `DENSITY_MATRIX`; parameters `BETA`, `MATSUBARA_HALF_N`, `MU`; optional
  `ETA`. Its tests (`run_input_data_loading_tests` sections A/B/C) are the
  compatibility gate.

### Conflict check with sibling stories

- **Story 05.2 (output file handler)** is orthogonal: it only adds the
  output path, the handler, and the Tensor write helper, and touches
  `main.cpp`/`gf2.cpp` writer and tests. 05.1 and 05.2 can land in either
  order with no overlapping hunks (05.1 never touches the writer; 05.2
  never touches the input framework).
- Stories 04/03/06.x are untouched (no Fourier, tail, Tensor-semantics, or
  solve API changes).

## Issues in the current code (the stragglers this story removes)

1. **`KeywordDefinition::required_for_gf2`** (`include/input.hpp`, used at
   `src/input.cpp` requirement check) is a calculation-specific boolean on a
   *generic* registry row. Adding a second calculation means adding
   `required_for_gw`, `required_for_xx`, ... — exactly the non-extensibility
   the brief calls out.
2. **Dataset layout/symmetry knowledge is hardcoded in calculation code.**
   `src/gf2.cpp` (`open_dataset`, `load_square_ao_matrix`, and the five
   hand-written load blocks inside `InputCatalog::require_gf2`) knows that
   `HCORE` is square `ao`×`ao` Hermitian, that `ERI3` is
   `{ao, ao, ri}` with a Symmetric AO pair, that `MO_COEFF` is
   `{mo, ao}` plain, and that every `ao` extent must match `HCORE`'s. The
   brief requires these to be **declared, in a single place, as keyword
   strings alongside axis DimLabels and symmetries** — i.e. as data in the
   framework, not as code in GF2.
3. **No string-keyed dataset access.** Callers only get the typed `Gf2Input`;
   the brief wants "refer to them simply by their strings and receive the
   corresponding Tensor".
4. **Entry validation is scattered and implicit.** The rank/type/extent
   checks and the symmetry construction are welded into the GF2 loader
   (issue 2); nothing in the framework declares *what a valid instance of
   each dataset is*, and nothing re-validates the produced tensor against
   such a declaration. (This story makes the declaration and the rank/type/
   extent checks definition-driven; the dedicated *symmetry validation pass*
   itself is deliberately split off into its own follow-up story — see
   *Decision 4* and *Deferred follow-up work*.)
5. **Minor stragglers:** `ResolvedInput::calc = Calc::Gf2` defaults a
   "validated" input to a concrete calculation (the parser always sets it;
   the default is a landmine), and `calc_name(Calc)` is a hardcoded switch
   that must be manually kept in sync with the set of calculations.

## Goals

1. **Per-calculation required/optional requirement sets, defined once and reused** (abstraction required by the brief): a calculation row lists its
   required datasets, required parameters, and optional keywords by
   canonical keyword string; the parser's missing-keyword check and the
   calculation-name resolution become *definition-driven* and the
   `required_for_gf2` field is deleted.
2. **Dataset definitions in a single place:** for every dataset keyword, its
   expected rank, its axis labels and their binding symmetry (SymKind), and
   its cross-dataset extent reference — the complete GF2 table below.
3. **String-keyed, generic dataset access**
   (`InputCatalog::require_dataset("DENSITY_MATRIX")`), cached in the
   catalog, with `require_gf2()` demoted to a thin typed wrapper over it.
4. **Definition-driven validation upon entry,** for every loaded dataset:
   element type (float64), declared rank, and the R1/R2 extent rules — all
   checked against the dataset definition, with clear needle-compatible
   diagnostics. (The dedicated *symmetry-validation pass* — checking the
   produced tensor's bindings, or the data values, against the declaration —
   is split off into its own follow-up story; this story still *declares and
   constructs* the bindings exactly as today.)
5. **Compatibility:** all existing `-t` tests pass unchanged; existing
   error messages remain needle-compatible; GF2 behavior is unchanged.

### Explicitly out of scope

- Adding any new calculation (GW etc. — the goal is only that adding one is
  a definitions-only edit, per the *extensibility* walkthrough below).
- Parser grammar, comment handling, value kinds, sanitizers, or
  double/int token rules — all unchanged.
- `Gf2Input` field layout and ownership (value-owning; tests construct and
  assign its fields), `make_gf2_initial_guess`, and everything downstream.
- **Entry symmetry-validation passes** on the produced tensors — neither
  structural (checking the tensor's per-axis `SymGroup`/label bindings
  against the declaration) nor numerical (verifying `hcore` is actually
  Hermitian within a tolerance, overlap positive-definiteness, etc.). Both
  are split off into their own follow-up story (see *Decision 4* and
  *Deferred follow-up work*); this story declares and constructs the
  symmetries as it does today, without re-validating them.
- Complex-valued input datasets, dataset groups/nesting, and per-calculation
  default overrides (defaults/sanitizers remain keyword-global; see
  Decision 5).

## Decisions

1. **Requirement sets are data, one table per calculation.** Replaces the
   per-calc bool. A `CalculationDefinition` row lists required and optional
   keyword *strings*; the parser consults the selected calculation's row.
   Adding a calculation = one row (+ its `Calc` enumerator + typed
   `require_*()`), zero edits to generic code.
2. **Dataset definitions are data, one row per dataset keyword**, carrying
   the rank, the axis labels (fastest→slowest, as `TensorDimLabel`s), the
   symmetry binding kind for the repeated-label family, and an optional
   cross-dataset extent reference. The *loader* becomes generic
   (definition-driven); the per-dataset GF2 code (`open_dataset`,
   `load_square_ao_matrix`, the five `require_gf2` load blocks) disappears
   from `src/gf2.cpp`.
3. **`require_dataset(keyword)` is the single loading entry point**, keyed
   by canonical keyword string (case-insensitive match, like keywords
   everywhere else), cached in the catalog; `require_gf2()` becomes:
   requirement-presupposition guard + five `require_dataset` calls + the
   existing scalar/range checks, returning the unchanged `Gf2Input`.
4. **Symmetry is declared and constructed in this story; its validation pass is
   split off into its own story.** The loader continues to construct each
   tensor with the declared labels and one fresh group per `def.symmetry`
   (unchanged Stories 05/07.1 behavior — the existing B1 section already
   asserts the constructed bindings), and entry validation covers **rank,
   element type, and the extent rules**. The brief's phrase "check the
   elements of the Tensors for the correct Symmetry" — i.e. a dedicated
   pass that checks a produced tensor (or its data values) against the
   declaration — is **out of scope for this pass**: it is its own follow-up
   story, with its sketch preserved in *Deferred follow-up work*. Rationale:
   keep this pass bounded to refactor + declaration + rank/type/extent
   validation; a validation pass needs its own test surface, and any
   value-level checks additionally need a tolerance policy that Stories 05
   and 07.1 already defer to the GF2 numerics.
5. **Defaults and sanitizers stay keyword-global** (a keyword's semantics
   belong to the keyword, not to a calculation): applying `ETA`'s default
   `1e-5` when the selected calculation is GF2 is unchanged; a future
   calculation sharing the keyword gets the same semantics for free.
   `optional` membership in a calculation row is informational (for future
   help output) and does not gate validation.
6. **`Calc::None` sentinel** replaces the `Calc::Gf2` default on
   `ResolvedInput`; a resolved input can never carry `None` (the parser
   enforces a valid calculation). `calc_name` is derived from the
   calculation registry (so there is exactly one list of known
   calculations).
7. **Single symmetry family per dataset (today).** The GF2 datasets need
   at most one binding (`ao` pair). The spec field is
   `std::optional<SymKind>` applied to the repeated-label family; a future
   dataset needing several families extends `DatasetDefinition` in its own
   story (see *Deferred*).

## Proposed API (definitions in `include/input.hpp` / `src/input.cpp`)

### 1. Calculation requirement sets (replace `required_for_gf2`)

```cpp
enum class Calc { None, Gf2 };                    // None: unselected sentinel only

// One row per supported calculation: its required/optional keyword sets.
// Keyword strings are CANONICAL (upper-case) spellings; order in each list
// is the order of missing-keyword reporting.
struct CalculationDefinition {
  Calc calc;
  std::string name;                                // "GF2"
  std::vector<std::string> required_datasets;      // e.g. { "HCORE", ... }
  std::vector<std::string> required_parameters;    // e.g. { "BETA", ... }
  std::vector<std::string> optional_keywords;      // defaulted keywords, e.g. { "ETA" }
};

const std::vector<CalculationDefinition>& calculation_registry();
[[nodiscard]] const CalculationDefinition& calculation_def(Calc calc);  // Calc::None -> std::logic_error

// calc_name now derived from the registry (single source of truth for names):
inline const char* calc_name(Calc calc);           // keeps returning "GF2" for Gf2, "?" for None
```

The GF2 row (must reproduce the existing set verbatim so the requirement
report is unchanged):

| field | content |
|-------|---------|
| `name` | `GF2` |
| `required_datasets` | `HCORE`, `MO_COEFF`, `ERI3`, `OVERLAP`, `DENSITY_MATRIX` (this order) |
| `required_parameters` | `BETA`, `MATSUBARA_HALF_N`, `MU` (this order) |
| `optional_keywords` | `ETA` |

Behavior changes in `parse_input` (all needle-compatible; see
*Compatibility contract*):

- **Calculation selection:** iterate `calculation_registry()` matching the
  `CALCULATION` value case-insensitively against `name`; set
  `resolved.calc`. Missing keyword → same "the 'CALCULATION' keyword is
  missing" error; unknown value → same "unrecognized calculation 'GWR'
  (known calculations: GF2)" error, with the "known calculations" list built
  from the registry.
- **Requirement check** (replaces `if (resolved.calc == Calc::Gf2) { ... }`
  and the `required_for_gf2` loop):

```cpp
const CalculationDefinition& cd = calculation_def(resolved.calc);
std::string missing;                       // datasets list order, then parameters list order
for (const std::string& kw : cd.required_datasets)   if (!values.count(kw)) missing += ...
for (const std::string& kw : cd.required_parameters) if (!values.count(kw)) missing += ...
if (!missing.empty())
  throw std::invalid_argument(cd.name + " calculation requires missing keyword(s): " + missing);
```

- `KeywordDefinition::required_for_gf2` is **deleted**; the registry rows
  keep exactly: `keyword`, `kind`, `default_value`, `sanitize`, `doc`.

### 2. Dataset definitions (the "single place")

```cpp
struct DatasetAxisSpec  { TensorDimLabel label; };      // e.g. "ao", "mo", "ri"

struct DatasetDefinition {
  std::string keyword;                 // canonical, e.g. "DENSITY_MATRIX"
  std::vector<DatasetAxisSpec> axes;   // FASTEST-to-slowest; rank == axes.size()
  std::optional<SymKind> symmetry;     // binding kind for the repeated-label family
                                       //   (Hermitian()/Symmetric() fresh group); nullopt = plain
  std::optional<std::string> extent_ref;  // keyword whose like-labelled axes fix this one's extents
  const char* doc;
};

const std::vector<DatasetDefinition>& dataset_definitions();
[[nodiscard]] const DatasetDefinition&
dataset_definition(const std::string& keyword);   // case-insensitive; unknown -> std::invalid_argument
```

The complete GF2 dataset table — the single source of truth (extents are
data-driven from the file; only labels and rules are declared):

| `keyword` | axes (fast→slow) | `symmetry` | `extent_ref` |
|-----------|------------------|------------|--------------|
| `HCORE` | `ao`, `ao` | `Hermitian` | — (defines the `ao` reference extent) |
| `MO_COEFF` | `mo`, `ao` | — (plain) | `HCORE` |
| `ERI3` | `ao`, `ao`, `ri` | `Symmetric` | `HCORE` |
| `OVERLAP` | `ao`, `ao` | `Hermitian` | `HCORE` |
| `DENSITY_MATRIX` | `ao`, `ao` | `Hermitian` | `HCORE` |

Extent rules applied to a dataset's *file shape* (slow→fast) before
construction:

- **R1 (repeated label):** all axes sharing a label that occurs more than
  once must have equal extents (i.e. an implicit squareness rule; the
  message retains the word *square*, per the compatibility contract).
- **R2 (reference):** if `extent_ref` is set and `extent_ref`'s dataset has
  an axis with the same label, this axis's extent must equal it (message
  retains "AO extent does not match <REF>").
- Axes whose label occurs nowhere in the reference are free (`mo`, `ri`).
- Ref recursion (a ref that itself has a ref) resolves by loading the ref
  through the same path; a self-reference or cycle is a `std::logic_error`
  (author error, unreachable with the shipped data).

### 3. Catalog: string-keyed access + generic load

```cpp
class InputCatalog {
public:
  // NEW: string-keyed dataset request (canonical keyword, case-insensitive).
  // Loads + validates per the dataset definition (rank/type/extent rules),
  // caches in the catalog, and returns the tensor by value. Repeated calls
  // return the (cached) same tensor; different keywords never share
  // storage.
  [[nodiscard]] Tensor<double, Executor::Host> require_dataset(const std::string& keyword) const;

  // UNCHANGED signature/return type; now a THIN wrapper: guard the selected
  // calculation, call require_dataset for each of its required datasets,
  // read the scalars (BETA/MATSUBARA_HALF_N/MU/ETA + provenance), and keep
  // the existing BETA/MU/HALF_N range re-checks.
  [[nodiscard]] Gf2Input require_gf2() const;
  // ... (from_file/from_text/resolved()/hdf5_path()/file() unchanged)

private:
  mutable std::map<std::string, Tensor<double, Executor::Host>> datasets_;  // load-once cache
};
```

Generic loader (lives in `src/input.cpp`; supersedes `open_dataset`,
`load_square_ao_matrix`, and the `require_gf2` load blocks in
`src/gf2.cpp`):

```text
require_dataset(keyword):
  def     = dataset_definition(keyword)                // unknown keyword -> invalid_argument
  if kw in datasets_            -> return copy
  if def.extent_ref             -> require_dataset(def.extent_ref) first   (recursive, guarded)
  path    = resolved_.get_string(keyword)              // not in input -> invalid_argument naming keyword
  ds      = file_.getDataSet(path)                     // missing -> "does not exist in the data file (...)" (keyword + path in message)
  if ds is not float64           -> "must have float64 elements (found ...)"
  if ds rank != def.axes.size() -> "must have rank N (found rank M)"
  apply R1 (repeated-label squareness)  -> "... a square ..."
  apply R2 (reference extents)          -> "... AO extent does not match <REF> ..."
  tensor  = Tensor<double, Host>{ TensorDim{label, extent, group?} ... }
             // ONE fresh group: Hermitian() / Symmetric() per def.symmetry,
             // shared by exactly the repeated-label axes; plain elsewhere
  ds.read_raw(tensor.data())             // C-order maps 1:1 (unchanged rule)
  datasets_[keyword] = tensor;  return tensor
```

### 4. `src/gf2.cpp::require_gf2` becomes (illustrative, complete)

```cpp
Gf2Input InputCatalog::require_gf2() const {
  if (resolved_.calc != Calc::Gf2)
    throw std::logic_error("InputCatalog::require_gf2: the resolved calculation is "
        + std::string(calc_name(resolved_.calc)) + ", not GF2");

  Gf2Input g;
  g.hcore          = require_dataset("HCORE");
  g.mo_coeff       = require_dataset("MO_COEFF");
  g.eri3           = require_dataset("ERI3");
  g.overlap        = require_dataset("OVERLAP");
  g.density_matrix = require_dataset("DENSITY_MATRIX");

  g.eta  = resolved_.get_double("ETA");
  g.eta_was_supplied = resolved_.supplied("ETA");
  g.beta = resolved_.get_double("BETA");
  g.matsubara_half_n = static_cast<size_t>(resolved_.get_int("MATSUBARA_HALF_N"));
  g.mu   = resolved_.get_double("MU");

  // Existing BETA/MU/MATSUBARA_HALF_N range re-checks: kept verbatim
  // (Story 07.1's boundary validation).
  ...
  return g;
}
```

`open_dataset` and `load_square_ao_matrix` are deleted; nothing else in
`src/gf2.cpp` (guess construction, writer) is touched.

### 5. `Gf2Input` — unchanged

Same fields, same order, same ownership (copyable/assignable by value; the
Story 07.1 tests construct `Gf2Input` and assign its tensor fields directly
— any move to reference-backed or non-copyable storage is a breaking
refactor explicitly out of this story). Only the header doc comment is
updated (the load path is now the catalog's definition-driven
`require_dataset`).

## Implementation notes (work order and mechanics)

### Work order (a strictly sequential plan; each step compiles or is
trivially isolated)

1. **`include/input.hpp`** (declarations only, nothing else yet):
   - delete the `required_for_gf2` field from `KeywordDefinition`;
   - add `Calc::None` to the enum;
   - declare `CalculationDefinition`, `calculation_registry()`,
     `calculation_def()` — these must appear **before** the inline
     `calc_name` that will reference `calculation_def`;
   - declare `DatasetAxisSpec` / `DatasetDefinition`,
     `dataset_definitions()` / `dataset_definition()`;
   - add `require_dataset` + the `mutable` cache member to `InputCatalog`;
   - update the file-header doc block (three-layer model is unchanged;
     the registry now carries per-calculation requirement sets and dataset
     specs) and the `KeywordDefinition` comment.
   - **No new `#include`s are needed**: `SymKind` is already visible via
     `gf2.hpp` → `symmetry.hpp`, `TensorDimLabel` via `tensor.hpp`, and
     `<map>` is already included.
2. **`src/input.cpp`** — the implementation body:
   - the two tables (GF2 calculation row; five dataset rows) as
     `static const` containers behind their accessors (same pattern as
     today's `keyword_registry`); they reference only literals, so there is
     no initialization-order hazard;
   - definition-driven calculation selection + requirement check in
     `parse_input` (replacing the two `if (resolved.calc == Calc::Gf2)`
     special cases);
   - `require_dataset` + the generic loader, **moved** out of
     `src/gf2.cpp` (see *Deletions* below), with the compatibility-contract
     message templates verbatim;
   - rewrite the ten `keyword_registry()` rows: drop the `required_for_gf2`
     initializer and its inline comment from each; keep row ORDER (it
     drives the `(known keywords: ...)` listing), kinds, defaults,
     sanitizers, and docs byte-for-byte.
3. **`src/gf2.cpp`** — `require_gf2` reduced to the thin wrapper (section 4
   of *Proposed API*); delete the helper block and load blocks (*Deletions*
   below). No other function in the file is touched.
4. **`include/gf2.hpp`** — doc-comment updates only.
5. **`src/tests.cpp`** — new cases (section *Testing plan*); full `./cppgw
   -t` green, then the manual acceptance commands.

### Cache mechanics

- **Key is the matched definition's CANONICAL keyword** (case-insensitive
  lookup first, then the canonical spelling is used), so
  `require_dataset("overlap")` and `require_dataset("OVERLAP")` hit the
  same cache entry.
- `mutable std::map<std::string, Tensor<double, Executor::Host>>` in
  `InputCatalog`; single-threaded by design, **no synchronization**
  (consistent with the rest of the codebase).
- Returns are by value = deep `Tensor` copies (existing copy semantics).
  Observable difference vs. today: a second `require_gf2()` in the same
  process performs **zero** HDF5 dataset reads (they are cached); a first
  call does exactly the same reads as it does today. No error path is
  affected by the cache (validation runs on the first load only).

### Loader mechanics

- Keep the existing **construct-then-read** shape: build the `Tensor` from
  the verified extents with the declared labels and (when
  `def.symmetry` is set) **one fresh group** (`Hermitian()` / `Symmetric()`)
  shared by exactly the repeated-label axes, then a single
  `ds.read_raw(tensor.data())` — no temp buffers, no transposition.
  (the C-order ↔ Tensor last-dim-fast mapping is the unchanged Story-05 rule).
- **Error path order (first match wins):** existence → element type →
  rank → R1 (repeated-label extents) → R2 (reference extents) →
  construct + read. This preserves today's observable order for every
  path covered by the existing tests (B2–B4).
- Message templates: the 2-D rows keep today's exact message strings
  (they satisfy the needles `square` and `AO`). The `ERI3` squaredness
  path (currently only reachable through the R2-style message) gets a
  dedicated message of the form `keyword ERI3: HDF5 dataset '<path>' must
  have equal extents on its repeated 'ao' axes (a square AO x AO pair;
  found R x C x C')` — not asserted by any existing test, only required to
  name the keyword and contain *square*.
- A dataset keyword absent from the resolved input surfaces through the
  existing `ResolvedInput::get_string` failure (`keyword <KW> is not set
  in the resolved input`) — no new message needed.
- An unknown/non-dataset keyword (e.g. a parameter) fails in
  `dataset_definition` **before any HDF5 access**, with:
  `'<keyword>' is not a known dataset keyword (known datasets: HCORE,
  MO_COEFF, ERI3, OVERLAP, DENSITY_MATRIX)` — the list built from the
  table, keeping one source of truth.

### `Calc::None` impact check (all call sites)

- `parse_input`: sets `resolved.calc` on the success path before any
  consumer runs (flow unchanged; a default-constructed `ResolvedInput`
  would be `None`, but no such value escapes the parser).
- `require_gf2` guard (`src/gf2.cpp`): unchanged; it reports
  `calc_name(resolved_.calc)` which returns `"?"` for `None` — that branch
  is unreachable in practice and the message still names the calculation.
- `main.cpp` `switch`: has `case Calc::Gf2:` with a fall-through
  "no implementation" message; `None` is unreachable from parsed input
  and, if it ever appeared, would report as "no implementation" —
  acceptable.
- Tests: no test inspects a default-constructed `ResolvedInput.calc`.

### Deletions (concrete, `src/gf2.cpp`)

- `struct ReadyDataset`, `open_dataset(...)`, `load_square_ao_matrix(...)`
  (the anonymous-namespace helper block at the top of the file), and
- the five dataset load blocks inside `require_gf2` (HCORE, MO_COEFF,
  ERI3, OVERLAP, DENSITY_MATRIX), including their hand-written extent
  checks (absorbed by the generic loader).
- **Kept in place:** the calculation guard, the scalar fetches
  (ETA ± provenance, BETA, MATSUBARA_HALF_N, MU), the BETA/MU/HALF_N range
  re-checks, `make_gf2_initial_guess`, and the output writer.
- All moved functions are TU-private or members, so **no CMake change and
  no linking surface changes**.

## Compatibility contract (what must NOT change)

- **CLI behavior** is identical: same accept/reject of invocations; same
  happy-path GF2 run; same exit codes.
- **Error messages remain needle-compatible** (the existing tests assert on
  substrings, so the *wording* below is part of the contract):
  - unknown keyword: `'<token>' is not a known keyword (known keywords: ...)`
  - duplicate keyword: `... is given more than once (first on line L1, again on line L2)`
  - missing `CALCULATION`: `... the 'CALCULATION' keyword is missing`
  - unknown calculation: `unrecognized calculation 'GWR' (known calculations: GF2)`
  - missing requirements: `GF2 calculation requires missing keyword(s): A, B, ...`
    (datasets in `required_datasets` order first, then parameters — for GF2
    this is the exact current order)
  - dataset missing: `keyword <KW>: HDF5 dataset '<path>' does not exist in the data file (...)`
  - element type: `keyword <KW>: ... must have float64 elements (found ...)`
  - rank: `keyword <KW>: ... must have rank N (found rank M)`
  - R1: `keyword <KW>: ... a square ... (found R x C)` (must contain *square*)
  - R2: `keyword <KW>: ... AO extent does not match <REF> (...)` (must contain *AO*)
