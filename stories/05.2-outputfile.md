# Story 05.2 — HDF5 output file handler and Tensor write helper

## Status, dependencies, and scope boundary

This is an **infrastructure story**, not a feature story. It introduces the
program's shared HDF5 **output file handler** so that every calculation writes
through one facility, fixes the output **filename rule** (today the name is a
hardcoded `"cppgw_output.h5"` in `main.cpp`), and adds the **Tensor-class
helper** for writing tensors to that output file. The existing ad-hoc GF2
writer from Story 07.1 (`write_gf2_output_hdf5` in `src/gf2.cpp`) is refactored
onto the new facility in the same pass, so the app has exactly one output path.

It applies facilities that already exist (HighFive via Story 1, `Tensor` from
Stories 06/06.1, the GF2 result from Story 07.1) and must **not** introduce a
new I/O framework beyond the one small handler specified below.

### Dependencies

- **Story 05 — Input parsing & data loading.** Provides `InputCatalog`, the
  normal run flow in `main.cpp::run_calculation`, the error policy
  (`std::invalid_argument` with actionable messages, exit 2), and the
  HighFive-based test conventions this story reuses.
- **Story 07.1 — GF2 initial Matsubara Green's-function guess.** Defines the
  GF2 **output content contract** this story standardizes (datasets `g0`,
  `sigma_hf`; attributes `eta`, `eta_was_supplied`, `beta`,
  `matsubara_half_n`, `n_matsubara`, `mu`). Story 07.1's
  `write_gf2_output_hdf5(input, guess, path)` already exists and this story
  refactors it; its output **names, shapes, dtypes, and values must stay
  identical** (see *GF2 output content (unchanged)* below). `tools/compare_gf2_testdata.cpp`
  and the reference file (`build/rhf_df_data.h5`) remain valid comparison
  targets without modification.
- `Tensor` (Story 06/06.1): dims ordered **fastest→slowest**, `data()`
  last-dim-fast, `rank()`, `dims()`.

This story does **not** depend on Story 05.1 (input-keyword API cleanup): it
touches the output path only, and does not add, remove, or rename any input
keyword, registry row, or `InputCatalog` API. If 05.1 lands first, 05.2's
diffs do not overlap 05.1's.

### Out of scope

- Any GF2/GW numerics, self-consistency, or new calculated quantities.
- Groups inside the output file, compression/chunking, parallel HDF5, multiple
  output files per run, appending to an existing output file, and writing
  device-resident tensors (only `Executor::Host` tensors are written).
- Per-calculation output *content* for calculations other than GF2 (each of
  those stories defines its own datasets/attributes and uses this handler).
- Building `tools/compare_gf2_testdata` into the CMake build (it remains a
  manual, one-shot tool; its source and the prebuilt binary in `build/` stay
  as-is).

## Context for implementation (current state)

- `src/main.cpp::run_calculation` hardcodes `const std::string out_path =
  "cppgw_output.h5";` and passes it to the GF2 writer after the calc branch.
- `src/gf2.cpp::write_gf2_output_hdf5` does everything by hand: rank/extent
  validation, two manual index-loop transposes (`g0` and `sigma_hf`) into
  `std::vector` buffers, two `createDataSet(...).write_raw(...)` calls, and six
  `createAttribute` calls.
- `Tensor` stores dims **fastest→slowest** (`Tensor::data()` is last-dim-fast),
  while HDF5 datasets are created with a shape listed **slowest→fastest**
  (C order). A `Tensor` therefore maps **zero-copy** onto a dataset whose
  shape (slowest→fastest) is the **reverse of the tensor's dim list** —
  exactly the rule the Story 05 load path relies on. When the desired file
  order differs (the GF2 `g0` **and** `sigma_hf` cases — see the mapping table
  below), a permuted
  copy is required — which is precisely what the manual loop in `gf2.cpp`
  does today and what the Tensor helper must support.
- Tests are in-process (`./cppgw -t`), self-contained, and use the established
  convention of a named file under `std::filesystem::temp_directory_path()`
  (e.g. `cppgw_story05_test.h5`), created with
  `HighFive::File f(path, HighFive::File::Truncate)` after
  `std::remove(path.c_str())`.

## Goals

1. **`OutputFile` handler:** one HDF5 output file per executable run, owned by
   the program (created in `main.cpp::run_calculation`), accessible to all
   calculation code without threading file handles through signatures.
2. **Filename rule:** the output file is named after the **input file**
   (`<input-stem>.h5` in the input file's directory), replacing the
   hardcoded `cppgw_output.h5`.
3. **Tensor helper:** `Tensor<T,E>::write(...)` / `Tensor<T,E>::write_to_output(...)`
   members (Story 05.2 requirement: "a helper function for the Tensor class")
   that create the dataset (correct name, element type, shape order) and copy
   the data with an explicit, unambiguous axis mapping.
4. **Refactor the GF2 writer** (`write_gf2_output_hdf5` → `write_gf2_output`)
   onto the handler + Tensor helper, preserving the output file format
   bit-for-bit (names, shapes, dtypes, values, attributes).
5. **Tests** for both the handler and the Tensor write paths in the `-t`
   suite, plus the CLI smoke checks below.

## Design decisions

- **One output file per process.** The handler holds a single *active* output
  file. `OutputFile::create(path)` opens the file with `HighFive::File::Truncate`
  (an existing file of that name is overwritten — calculation output is always
  replaced, never appended) and makes it the active file; calling it again
  replaces the active file with the new one (this keeps the in-process test
  suite able to use separate output files; the production flow calls it
  **exactly once**, right after the catalog is resolved).
- **`Tensor` gets a member helper, defined out-of-line.** `tensor.hpp` must not
  start including the full HighFive header (it is a performance-critical core
  header included by many TUs, most of which never touch HDF5). So `tensor.hpp`
  gains only forward declarations (`namespace HighFive { class File; }` and
  `class OutputFile;`) plus the two member *declarations*; the
  out-of-line template definitions and explicit instantiations live in the new
  `src/output.cpp` (next to the handler, where HighFive is fully included).
  Instantiations are required for the scalar types used in this story:
  `double` and `std::complex<double>`, both for `Executor::Host`. A future
  calculation that writes a new scalar type adds one explicit instantiation
  line — nothing else.
- **Explicit axis mapping, never size-inference.** The permuted write takes an
  **axis-index** map, not a target shape. Resolving the permutation from axis
  *sizes* alone is ambiguous for degenerate extents (a 24×24 matrix: identity
  vs. transpose are indistinguishable by size but produce different data), so
  size-based inference is forbidden; the caller always says which tensor axis
  goes to which file axis. The default (no map) is the zero-copy order
  `file_axis = {rank-1, rank-2, ..., 0}`, i.e. the dataset shape is the
  tensor's dim list reversed — the same convention as the input-file layout
  (`hcore` → shape `(ao, ao)`, `mo_coeff` → shape `(ao, mo)`).
- **Collision guard.** The derived output path must not resolve to the input
  **data** file path; the check happens in `run_calculation` (which sees both
  paths) **before** `OutputFile::create`, comparing
  `std::filesystem::absolute(p).lexically_normal()` strings case-sensitively
  (POSIX). This is the class of failure the old hardcoded name could
  accidentally cause (input named `cppgw_output.h5.in`), and it is the reason
  the naming rule needs an explicit guard instead of a blanket convention.
- **The GF2 output file is unchanged in content.** Same dataset names
  (`g0`, `sigma_hf`), same shapes, same element types, same six attributes,
  same values. Only the plumbing (who opens the file, where the name comes
  from, how the data is copied) changes. `tools/compare_gf2_testdata.cpp` keeps
  working against the new file with one argument changed (the path).
- **Error policy** matches Story 05: `std::invalid_argument` naming the
  offending object (dataset name / axis / path) for programmer- or
  input-caused problems, `std::logic_error` for programming-order violations
  (using the active output file before `create`); HighFive open/write failures
  propagate. All of these surface through the existing `main` catch as
  `cppgw: <message>` and exit code 2.
- **`std::filesystem`** is used for the name derivation (C++20 is already the
  project standard); no new third-party dependency is introduced.

## Filename rule

`output_path_for(input_path)` — the single place the rule is implemented:

```text
output_path = parent_dir(input_path) / ( stem(input_path) + ".h5" )
```

i.e. `std::filesystem::path p(input_path); return (p.parent_path() / (p.stem() + ".h5")).string();`

| input path        | output path         |
|-------------------|---------------------|
| `build/test.in`   | `build/test.h5`     |
| `test.in`         | `test.h5`           |
| `/tmp/a/run`      | `/tmp/a/run.h5`     |
| `/tmp/a/my.2.in`  | `/tmp/a/my.2.h5`    |

Notes: the input file may carry any (or no) extension (Story 2); the rule
strips exactly the last extension and appends `.h5`. Overwrite-on-exist is the
defined behavior (`Truncate`); the **only** forbidden target is the data file
itself (collision guard, above). An empty input path is not a valid invocation
(Story 2 already rejects missing input), so no special case is needed.

## Proposed API

### `include/output.hpp` (new)

```cpp
#pragma once
// ============================================================================
//  Output file handler (Story 05.2)
//  One HDF5 output file per executable run...
// ============================================================================
#include <highfive/highfive.hpp>
#include <string>

namespace cppgw {

/// Output path rule: same directory as the input file, same stem, ".h5" suffix.
/// `output_path_for("build/test.in") == "build/test.h5"`.
std::string output_path_for(const std::string& input_path);

/// The single, process-wide output file (Story 05.2: one output file per run).
class OutputFile {
public:
  // Open `path` for WRITING (HighFive::File::Truncate semantics: any
  // pre-existing file is replaced) and make it the ACTIVE output file.
  // May be called again to replace the active file (tests); the
  // production flow calls it exactly once, right after the input
  // collision guard passes.
  static void create(const std::string& path);

  // The active output file. Throws std::logic_error if create() has not
  // been called (programming-order violation, not an input error).
  static HighFive::File& file();

  // The active output file's path (diagnostic messages).
  static const std::string& path();
};

} // namespace cppgw
```

### `src/output.cpp` (new)

- `output_path_for` as specified above.
- `OutputFile` state: function-local `static` storage in this file,
  `std::unique_ptr<HighFive::File> the_file;` and `static std::string the_path;`
  (plus an atomic or plain-guard note: all use is single-threaded; no
  synchronization is added). `create` resets `the_file` and stores `the_path`.
- Out-of-line definitions of `Tensor::write` and `Tensor::write_to_output`
  (below) and their explicit instantiations:

```cpp
template void Tensor<double, Executor::Host>::write(const std::string&, HighFive::File&,
                                                    const std::vector<size_t>&) const;
template void Tensor<double, Executor::Host>::write_to_output(const std::string&,
                                                              const std::vector<size_t>&) const;
template void Tensor<std::complex<double>, Executor::Host>::write(const std::string&,
                                                                  HighFive::File&,
                                                                  const std::vector<size_t>&) const;
template void Tensor<std::complex<double>, Executor::Host>::write_to_output(
    const std::string&, const std::vector<size_t>&) const;
```

### `include/tensor.hpp` (additions only)

Forward declarations near the top, inside `namespace cppgw`:

```cpp
namespace HighFive { class File; }
class OutputFile;
```

Two member declarations inside `class Tensor` (near the other public I/O-ish
members, e.g. after `data()`), with a comment cross-referencing Story 05.2:

```cpp
  // ----- Story 05.2: HDF5 output (defined in src/output.cpp) -----
  //
  // Write this tensor to dataset `name` in the given HDF5 file.
  //
  // file_axis maps file axis i (0 = SLOWEST / outermost, the natural HDF5
  // "C-order" position) to the tensor axis (index into dims(); 0 = fastest)
  // that occupies it. The dataset shape is dims()[file_axis[i]].dim for
  // i = 0..rank-1. The default (empty) map is {rank-1, ..., 0}: the dataset
  // shape is the tensor's dim list reversed and the write is a direct,
  // zero-copy write_raw of data(). Any other valid permutation is copied
  // through a temporary buffer (element-exact; see algorithm below).
  //
  // Throws std::invalid_argument naming `name` if file_axis is the wrong
  // length, out of range, or not a permutation.
  void write(const std::string& name, HighFive::File& file,
             const std::vector<size_t>& file_axis = {}) const;

  // Same, but writes into the ACTIVE output file (OutputFile::file());
  // throws per OutputFile::file() if none has been created.
  void write_to_output(const std::string& name,
                       const std::vector<size_t>& file_axis = {}) const;
```

Write algorithm (implement once for `write`; `write_to_output` delegates with
`OutputFile::file()`):

1. `r = rank();` If `file_axis.empty()`, substitute `{r-1, r-2, ..., 0}`
   (the identity/zero-copy mapping).
2. Validate: `file_axis.size() == r`; every entry `< r`; all distinct.
   Otherwise `std::invalid_argument("Tensor::write: dataset '<name>':
   invalid axis mapping ...")`.
3. `shape[i] = dims()[file_axis[i]].dim` (i = 0..r-1) → `HighFive::DataSpace`.
4. If the map is the identity/zero-copy one:
   `file.createDataSet<scalar_type>(name, shape).write_raw(data());`
   Otherwise: allocate `std::vector<scalar_type> buf(total_elements())`;
   for every linear index `p`, decompose it into tensor indices
   `t[j] = (p / strides_[j]) % dims_[j].dim` (j = 0..r-1), compute the file
   offset `fl = Σ_i t[file_axis[i]] * fstride[i]` where `fstride` is the
   C-order stride order of `shape`, and set `buf[fl] = data()[p]`; then
   `createDataSet<scalar_type>(name, shape).write_raw(buf.data())`.
5. Element type follows `scalar_type` exactly as HighFive emits it today:
   `double` → `H5T_NATIVE_DOUBLE`; `std::complex<double>` → the two-`double`
   compound struct — the same dtypes as the current Story 07.1 output.

Concrete mapping for the two GF2 datasets (this is the only permuted write in
the codebase today):

| dataset | tensor (dims fastest→slowest) | `file_axis` | file shape | zero-copy? |
|---------|-------------------------------|-------------|------------|------------|
| `sigma_hf` | `{ ao_row(u), ao_col(v) }` (both N_AO) | `{ 0, 1 }` | `(N_AO, N_AO)` | no (transpose copy) |
| `g0` | `{ matsubara(n), ao_row(u), ao_col(v) }` | `{ 0, 1, 2 }` | `(N_M, N_AO, N_AO)` | no (transpose copy) |

Both mappings are **explicit**, not the default: the reference-file
convention (used by `tools/compare_gf2_testdata`, which reads
`sout[u*nao+v]` and `gout[n*nao*nao+u*nao+v]`) is **first coordinate slowest
in the file** — `file[u,v] = Σ(u,v)`, `file[n,u,v] = G(n,u,v)`. Since the
tensor's first coordinate is its *fastest* axis, the default (zero-copy) map
would store the transpose (`u` fastest in the file) and the K-energy terms
of `σ_HF` (not bitwise symmetric) would then fail the reference comparison.
An implementation may only switch a dataset to the default map if the data
is known bitwise-symmetric in the affected axes; neither `sigma_hf` nor `g0`
is, so both keep the explicit maps above.

### `include/gf2.hpp` / `src/gf2.cpp` (refactor)

Rename `write_gf2_output_hdf5` → `write_gf2_output`, drop the `path` argument
(it writes to the **active** output file), and re-implement on the handler:

```cpp
/// @brief Write the bounded Story 07.1 results to the ACTIVE output file
///        (OutputFile::create is called exactly once by main; Story 05.2).
///
/// Datasets (C-order), unchanged from the Story 07.1 contract:
///   g0       : (n_matsubara, nao, nao), complex128, G_0(iw_n) ascending in n
///   sigma_hf : (nao, nao), float64, the static restricted HF self-energy
/// File attributes (calculation input parameters only):
///   eta, eta_was_supplied, beta, matsubara_half_n, n_matsubara, mu
void write_gf2_output(const Gf2Input& input, const Gf2InitialGuess& result);
```

New body (keep the three existing extent/rank validations verbatim):

```cpp
const size_t n_matsu = result.green.size();
// Explicit axis maps, NOT the default: the reference-file convention is
// file[u,v] = Sigma(u,v) / file[n,u,v] = G(n,u,v) (see the mapping table),
// i.e. the first tensor coordinate is slowest in the file.
result.sigma_hf.write_to_output("sigma_hf", {0, 1});    // (N_AO, N_AO), transpose copy
result.green.data().write_to_output("g0", {0, 1, 2});   // (N_M, N_AO, N_AO), transpose copy
auto& f = OutputFile::file();
f.createAttribute("eta", input.eta);
f.createAttribute("eta_was_supplied", static_cast<int>(input.eta_was_supplied));
f.createAttribute("beta", input.beta);
f.createAttribute("matsubara_half_n", static_cast<long long>(input.matsubara_half_n));
f.createAttribute("n_matsubara", static_cast<long long>(n_matsu));
f.createAttribute("mu", input.mu);
```

(The six attribute writes and the two dataset writes above are the **entire**
GF2 output content; see the unchanged contract table, and note the Green's
function is a `GridExpansionMatsubara` whose `data()` tensor is written — the
expansion's grid parameters are recorded as attributes, not re-derived.)

## Testing plan (all in-process via `./cppgw -t`)

New dedicated function `int run_output_file_tests();` added to `src/tests.hpp`,
wired into `run_tests()` immediately after `run_input_data_loading_tests();`
(same pattern as every other story: throws `std::runtime_error` on any
failure). Temp-file convention follows Story 05 section B:

```cpp
const std::string h5 = (std::filesystem::temp_directory_path() / "cppgw_output_test.h5").string();
std::remove(h5.c_str());
```

Cases (deterministic, small, no external fixtures):

1. **`output_path_for` (pure):** `("test.in" → "test.h5")`,
   `("build/test.in" → "build/test.h5")`, `("/a/b/run" → "/a/b/run.h5")`,
   `("/a/b/my.2.in" → "/a/b/my.2.h5")`.
2. **`OutputFile` handler:** `OutputFile::file()` before `create` throws
   `std::logic_error`; `create(path)` + `path()` returns the path given;
   a tensor written via `write_to_output` is visible through
   `OutputFile::file().hasDataSet(...)`; calling `create` again makes the new
   path/file active.
3. **Direct (zero-copy) write:** `Tensor<double,Host>` with dims
   `{ i = 2 (fastest), j = 3 (slowest) }`, stored as `t(i, j)` with all
   distinct values, written with the default map (`write("m2", f)`) into a
   locally opened `HighFive::File` (tests of `write` do NOT require the
   active-file handler). Assert the dataset shape is `{3, 2}` and every
   element satisfies `buf[j*2 + i] == t(i, j)` (the fastest tensor coordinate
   is the fastest file coordinate, per the default mapping rule).
4. **Permuted write:** `Tensor<double,Host>` `{ a=2, b=3, c=5 }`
   (fastest→slowest, all distinct values), written with
   `write("m3", f, {0, 2, 1})`. By the mapping rule, file axis *i* (0 =
   slowest) holds tensor axis `file_axis[i]`, so the tensor axes land as
   (slow→fast) = `a, c, b`, and the dataset shape is
   `shape[i] = dims()[file_axis[i]].dim` = **`(2, 5, 3)`**.
   Element-exact check with file coordinates `f0` (slowest, size 2), `f1`
   (size 5), `f2` (fastest, size 3):
   `buf[f0*15 + f1*3 + f2] == t(f0, f2, f1)` for every `f`
   (i.e. `a = f0`, `b = f2`, `c = f1`).
   Also: `write` with a duplicate / out-of-range / wrong-length map throws
   `std::invalid_argument` whose message contains the dataset name.
5. **Complex round-trip:** `Tensor<std::complex<double>,Host>` 2×2 (distinct
   real/imag parts), direct write; read back both fields exactly.
6. **GF2 end-to-end through the handler:** reuse the `make_manual_input(2, 2)`
   fixture already present in Story 07.1's tests (section C of
   `run_input_data_loading_tests`): build the guess,
   `OutputFile::create(<temp path>)`, `write_gf2_output(in, guess)`; then
   reopen the file read-only and assert: `g0` shape
   `(2*half_n, 2, 2)` and every `g0(n,u,v) → buf[n*4 + u*2 + v] ==
   result.green.data()(n, u, v)`; `sigma_hf` shape `(2, 2)` and exact equality
   element-by-element (`buf[u*2 + v] == result.sigma_hf(u, v)`) — this last
   is exactly the reference convention, and it would **not** hold if the
   default zero-copy map were used on a non-symmetric matrix (see the
   mapping table); all six attributes present with the input's exact values
   (this is the in-process stand-in for the reference-file comparison).
7. **Existing suite stays green:** every prior section (Stories 2–4, 5, 6/6.1,
   6.2, 7.1) still passes unchanged, including the Story 07.1 residual/analytic
   checks.
