# Story 06.1 — General Tensor axis permutation and transpose

## Dependencies

- **Story 06 — Tensor index symmetry & the Tensor backend seam**
- **Story 05 — Input parsing & data loading**, only for the GF2 integration tests
- Existing Tensor storage and layout conventions

## Motivation

Story 06 deliberately implemented only the symmetry-aware *no-op* form of
`Tensor::transpose(i, j)`. It is useful for declared symmetric, Hermitian, and
antisymmetric index pairs, but it throws for two genuinely distinct axes:

```cpp
Tensor::transpose(i, j)
```

is currently not a general data-moving transpose.

That limitation becomes a practical blocker for GF2 and later tensor
algorithms. Real calculations need to reorder axes in order to:

- place a contraction axis in the position required by `gemm`;
- interpret an HDF5 dataset using physical labels without assuming one storage
  order forever;
- transform both AO axes of a matrix-valued quantity;
- prepare a tensor for a backend with a different preferred layout;
- undo or compose arbitrary contraction layouts.

This story adds a genuine axis-permutation operation while preserving the
philosophy established by the previous stories:

1. **Tensor owns labels, shapes, symmetry metadata, and validation.**
2. **The backend owns dense-buffer data movement and numerical kernels.**
3. **Symmetry is advisory metadata.** It is not used to compress storage or
   silently change a general permutation.
4. **The Tensor has no view type yet.** A permutation therefore returns an
   independently owned, deep-copied Tensor.
5. **The storage convention is explicit.** Tensor dimensions are ordered
   fastest-to-slowest, with `dims()[0]` contiguous and stride 1.

The goal is not to add an optimizing tensor compiler or a full contraction
planner. The goal is a small, correct, composable primitive that later stories
can rely on.

---

## Current behavior to preserve

Story 06 currently defines `Tensor::transpose(i, j)` as a symmetry-aware
operation:

- a pair in the same non-null `SymGroup` is accepted;
- `Symmetric` returns an elementwise-identical copy;
- real `Hermitian` returns an elementwise-identical copy;
- complex `Hermitian` returns an elementwise-conjugated copy;
- `Antisymmetric` returns an elementwise-negated copy;
- a pair of genuinely distinct axes throws a `std::logic_error` saying that
  active transpose is not yet implemented.

This behavior is covered by Story 06 tests and must remain compatible unless
this story explicitly updates those tests and documentation.

The new implementation must therefore distinguish two related operations:

### Semantic pair transpose

```cpp
Tensor transpose(size_t i, size_t j) const;
```

This remains the public pairwise operation. For a pair belonging to one
symmetry group, it retains the Story 06 shortcut. For a pair that does not
belong to one symmetry group, it performs a physical two-axis permutation.

### General physical axis permutation

```cpp
Tensor permute_axes(std::span<const size_t> permutation) const;
```

This is the general layout operation. It reorders axes and data according to
the supplied permutation. It is deliberately a physical permutation:

- it moves data;
- it moves `TensorDim` metadata with the corresponding axes;
- it does not infer, enforce, or exploit symmetry;
- it does not apply conjugation or negation merely because two axes belong to a
  declared symmetry group.

This distinction prevents the symmetry metadata from becoming an implicit
storage/computation policy. `transpose(i, j)` remains the semantic convenience
operation required by Story 06; `permute_axes` is the general dense-layout
primitive needed by later algorithms.

If the project later decides that `transpose(i, j)` should become purely
physical for all pairs, that should be a separate API decision and story, not
an accidental consequence of implementing this one.

---

## Goals

1. Implement a correct general axis permutation for host Tensors.
2. Extend `Tensor::transpose(i, j)` to physically swap distinct axes.
3. Preserve Story 06 symmetry behavior for same-group pairs.
4. Preserve and reorder all `TensorDim` metadata, including labels and
   `SymGroup` handles.
5. Keep the backend unaware of labels and symmetry.
6. Make the permutation convention unambiguous and test it on rectangular,
   non-adjacent, and rank-three tensors.
7. Make the implementation safe for identity permutations, rank-zero/rank-one
   tensors, zero-sized dimensions, and independently copied outputs.
8. Provide a clean basis for future GF2 data-loading and contraction-layout
   stories.

---

## Out of scope

- Tensor views or zero-copy transposes.
- In-place permutation of an existing Tensor.
- Automatic contraction planning.
- Automatic insertion of transposes around `gemm`.
- Storage compression from symmetry.
- Symmetry validation against tensor data.
- Multi-member/transitive symmetry algebra beyond the existing `SymGroup`
  metadata model.
- GPU/device permutation kernels. The backend contract may be prepared for
  them, but only the existing host executor is required in this story.
- A general reshape operation. A permutation changes axis order but not the
  logical dimensions or number of elements.
- Changing the public meaning of `Symmetric`, `Hermitian`, or `Antisymmetric`.

## Terminology and layout contract

A Tensor stores dimensions in **fastest-to-slowest** order:

```text
dims()[0]                 fastest, stride 1
dims()[1]                 next fastest
dims()[rank - 1]          slowest
```

For dimensions with sizes `D[0], D[1], ..., D[R-1]`, the flat offset of
coordinates `x[0], ..., x[R-1]` is:

```text
offset(x) = x[0]
             + D[0] * x[1]
             + D[0] * D[1] * x[2]
             + ...
```

The permutation convention is:

```text
permutation[new_axis] = old_axis
```

For example, for a rank-three Tensor:

```text
input dimensions:  [a, b, c]
permutation:       [2, 0, 1]
output dimensions: [c, a, b]
```

For an output coordinate `y`, the corresponding input coordinate `x` is:

```text
x[permutation[new_axis]] = y[new_axis]
```

Equivalently, the output axis `j` contains the old axis
`permutation[j]`.

This convention is preferable to an old-to-new mapping because the output
shape can be constructed directly:

```cpp
out_dims[new_axis] = in_dims[permutation[new_axis]];
```

The permutation must contain every integer in `[0, rank)` exactly once.

## Proposed API

The exact spelling may be adjusted during implementation, but the semantics
must remain explicit.

### General permutation

```cpp
Tensor permute_axes(std::span<const size_t> permutation) const;
```

Convenience overloads should make normal use easy without making the range
semantics ambiguous:

```cpp
Tensor permute_axes(const std::vector<size_t>& permutation) const;
Tensor permute_axes(std::initializer_list<size_t> permutation) const;
```

If the implementation uses a constrained range instead of these overloads,
the same `permutation[new_axis] = old_axis` convention must be documented in
the public API.

Requirements:

- `permutation.size() == rank()`;
- each axis index is in range;
- no axis occurs twice;
- all axes occur exactly once;
- output dimensions are the input dimensions reordered by the permutation;
- output storage is independently owned;
- output values satisfy the coordinate mapping above.

An identity permutation is valid and returns an independent deep copy. It must
not return an alias to the source buffer.

### Pairwise transpose

```cpp
Tensor transpose(size_t i, size_t j) const;
```

Behavior:

1. If either axis is out of range, throw `std::logic_error` or
   `std::out_of_range` according to the project's finalized error policy.
   The chosen exception type must be documented and tested.
2. If `i == j`, return an elementwise-identical deep copy. Transposing an axis
   with itself must not conjugate or negate data, even if that axis has a
   symmetry handle.
3. If `dims_[i].symmetry` and `dims_[j].symmetry` are the same non-null
   `SymGroup`, retain the Story 06 symmetry-aware behavior:
   - `Symmetric`: identity copy;
   - real `Hermitian`: identity copy;
   - complex `Hermitian`: conjugated copy;
   - `Antisymmetric`: negated copy.
4. Otherwise, construct the swap permutation and call the general physical
   permutation operation.

The pairwise method is therefore convenient for both cases:

```cpp
x.transpose(0, 2);       // physical swap if axes are distinct
x.transpose(1, 2);       // Story 06 symmetry shortcut if bound as one group
```

The implementation must not silently reinterpret a distinct-axis transpose as
an elementwise operation.

### Optional named aliases

If the implementation team finds `transpose` and `permute_axes` too easy to
confuse, a named alias may be provided:

```cpp
Tensor permute(std::span<const size_t> permutation) const;
```

There should still be one canonical implementation. `transpose(i, j)` should
be a small wrapper around either the symmetry shortcut or a swap permutation.

## Metadata and symmetry policy

### TensorDim metadata

For a physical permutation, metadata moves with its axis:

```cpp
out.dims()[new_axis] = in.dims()[permutation[new_axis]];
```

This includes:

- the `TensorDimLabel` variant;
- the dimension size;
- the exact `SymGroup` shared-pointer handle.

The operation must not create new symmetry groups, compare groups by kind, or
merge groups merely because their `SymKind` values match.

For example, if the input contains two independent symmetric families with
distinct handles, the output must contain those same two independent handles
after permutation.

### Duplicate labels

The existing Story 06 invariant remains in force. A permutation cannot create a
new invalid label arrangement because it only reorders an already-valid set of
`TensorDim` objects. Nevertheless, the output should run the normal shape and
symmetry validation rather than bypassing it.

### Same-group pair transpose

For the Story 06 semantic `transpose(i, j)` shortcut, no physical axis
permutation is necessary because the group members have equal size and the
operation is defined by the declared relation.

For the general `permute_axes` primitive, symmetry is only metadata. If a caller
explicitly supplies a permutation that exchanges members of a symmetry group,
`permute_axes` performs the raw coordinate permutation and does not apply
conjugation or sign changes. This distinction must be documented prominently.

This keeps the backend and physical-layout primitive symmetry-agnostic, as
required by Story 06.

### Symmetry propagation

No new symmetry is inferred. Since metadata travels with axes, existing
`SymGroup` handles are preserved, but no symmetry is derived from data or from
an arbitrary relationship between different axes.

## Backend integration

A general transpose is a dense data-movement operation. It belongs behind the
same backend seam as `gemm` and the existing unary operations, while all label
and permutation validation remains in `Tensor`.

The frontend should:

1. validate the permutation;
2. construct the reordered `std::vector<TensorDim>`;
3. allocate the output Tensor;
4. provide the backend with raw buffers, dimensions, strides, and the validated
   permutation;
5. return the output.

The backend must not receive or inspect `TensorDimLabel`, `SymGroup`, or
function-space tags.

A possible host backend operation is:

```cpp
template <typename T>
static void permute(
    const TensorBuffer<T, Executor::Host>& source,
    std::span<const size_t> source_dims,
    std::span<const size_t> permutation,
    TensorBuffer<T, Executor::Host>& destination);
```

The exact signature may instead pass source and destination strides or output
dimensions. The contract must make clear that:

- source and destination are dense buffers;
- `permutation[new_axis] = old_axis`;
- the destination is already allocated with the reordered shape;
- source and destination do not alias in this story;
- the backend performs no label/symmetry validation.

### Initial host implementation

The first host implementation may use a straightforward coordinate loop. It
must prioritize correctness and readable indexing over optimization.

The implementation should avoid recursive per-element Tensor access because
that would repeat bounds checks and potentially make the operation needlessly
expensive. It should compute source and destination flat offsets using the
known dimensions/strides.

A later optimization story may add:

- contiguous-block detection;
- special cases for identity and adjacent swaps;
- tiled copies;
- BLAS/backend-specific layout operations;
- device kernels.

### Aliasing

The public operation returns a new Tensor and therefore has non-overlapping
source/destination storage. In-place permutation is out of scope. The backend
contract should not imply that source and destination alias safely.

## Interaction with `gemm`

The purpose of this story is not to make `gemm` automatically reorder inputs.
Existing `gemm` semantics remain unchanged:

- X's contracted axis is its last/slowest axis;
- Y's contracted axis is its first/fastest axis;
- the result has X's remaining axes followed by Y's remaining axes.

A caller may now explicitly arrange an operand:

```cpp
auto prepared = x.permute_axes({ /* desired old axes */ });
gemm(prepared, y, z, label_x, label_y);
```

No implicit permutation should be added inside `gemm` in this story. That would
hide allocations and make performance difficult to reason about.

The story should add at least one test showing that a tensor can be permuted
into a `gemm`-compatible layout and then contracted successfully.

---

## HDF5 and GF2 integration

Story 05 currently assumes that loaded datasets already have an order that can
be copied directly into Tensor storage. This story should not silently change
that loader behavior, but it should make explicit how a future loader can use
permutation.

For a dataset whose physical/storage axes do not match the desired Tensor label
order, the loader may eventually:

1. read the dense source tensor in the dataset's native order;
2. construct source dimensions describing that order;
3. call `permute_axes` to produce the labelled working order.

This is preferable to embedding axis-specific nested loops into every loader.

The implementation story may include a small synthetic HDF5 test, but it must
not broaden Story 05's accepted file schema. Real GF2 data loading remains a
separate concern.

---

## Error handling

Validation errors must identify the operation and the offending permutation.
At minimum, errors should distinguish:

- wrong permutation length;
- an axis index outside `[0, rank)`;
- a duplicate axis index;
- an omitted axis;
- transpose index out of range;
- attempting to use an unimplemented device backend, if applicable.

Recommended exception categories:

- `std::invalid_argument` for a malformed permutation;
- `std::out_of_range` for an axis index outside the Tensor rank;
- `std::logic_error` only for an unavailable executor/backend operation.

The project may choose a different split, but it must be consistent with the
existing Tensor API and covered by tests.

No partial output should be exposed if validation or allocation fails.

## Numerical and implementation pitfalls

### 1. Do not reverse the permutation convention

The most likely implementation error is confusing:

```text
output axis -> input axis
```

with:

```text
input axis -> output axis
```

The story's required convention is:

```text
permutation[new_axis] = old_axis
```

Tests must use non-self-inverse permutations such as `[2, 0, 1]`, not only
simple swaps, because a reversed convention can accidentally pass swap tests.

### 2. Do not assume axes have equal dimensions

Distinct axes may be rectangular and have different sizes. A correct
implementation must support, for example:

```text
[a=2, b=3, c=4] -> [c=4, a=2, b=3]
```

The same-size restriction applies only to axes in one symmetry group.

### 3. Do not use labels as physical positions

Labels can be duplicated for symmetry-bound axes. General permutation must use
axis positions, not `label_index`, to identify coordinates. A label is not a
sufficient description of one physical axis when it belongs to a symmetry
family.

### 4. Preserve storage order semantics

After the permutation, recompute output strides from the reordered dimensions.
Do not merely swap the `dims_` vector while leaving the old strides or buffer in
place.

### 5. Handle rank zero and zero-sized dimensions

A default/unallocated Tensor and a Tensor with a zero-sized dimension need
explicit behavior. Recommended behavior:

- a default/unallocated Tensor may only accept an empty permutation and returns
  an unallocated deep copy, or it may reject the operation consistently with
  other Tensor operations;
- a rank-zero allocated state is treated as a scalar with the empty
  permutation;
- a Tensor with a zero-sized dimension preserves the reordered metadata and
  remains unpopulated without dereferencing a null data pointer.

The implementation must choose and document the behavior rather than relying on
pointer arithmetic over zero elements.

### 6. Avoid accidental symmetry changes

Do not create a new `SymmetryGroup` while reordering dimensions. Shared-pointer
identity is part of the current API contract.

### 7. Avoid accidental aliases

The result must not share the source `TensorBuffer`. Modifying the result after
the permutation must not modify the source.

### 8. Complex Hermitian semantics are only for `transpose(i,j)`

The existing complex-Hermitian conjugation rule applies to the semantic
same-group pair operation. It must not unexpectedly appear in the lower-level
`permute_axes` data movement operation.

## Tests

Add tests to the existing Story 06 tensor/symmetry test suite, or create a
small dedicated test function wired into `run_tests()` using the repository's
current in-process test style.

### 1. Identity permutation

For a rank-three Tensor:

```text
permutation = [0, 1, 2]
```

Verify:

- rank and dimensions are unchanged;
- every element is unchanged;
- the result is independently owned;
- modifying the result does not modify the source.

### 2. Non-self-inverse rank-three permutation

Use a Tensor with dimensions:

```text
[a=2, b=3, c=4]
```

Fill values using a coordinate-dependent formula, then apply:

```text
[2, 0, 1]
```

Verify the output dimensions are:

```text
[c=4, a=2, b=3]
```

and for every output coordinate `(c, a, b)`:

```text
out(c, a, b) == in(a, b, c)
```

This test catches reversed permutation conventions.

### 3. Pairwise transpose of distinct axes

Use a rectangular matrix:

```text
[a=2, b=3]
```

Call `transpose(0, 1)` and verify:

```text
out dims = [b=3, a=2]
out(b, a) = in(a, b)
```

Also verify that `transpose(1, 0)` produces the same values and shape.

### 4. Non-adjacent transpose

Use rank four dimensions with all different sizes and swap axes 0 and 3.
Verify both metadata order and coordinate mapping. This catches
implementations that only handle adjacent axes.

### 5. Arbitrary permutation round trip

For a non-self-inverse permutation `p`, compute its inverse `p_inv` under the
story's convention and verify:

```text
x.permute_axes(p).permute_axes(p_inv)
```

has the same dimensions and values as `x`.

### 6. Metadata preservation

Construct a Tensor with:

- different string labels;
- grid or Chebyshev labels;
- two independent symmetry groups;
- duplicate labels within each group.

Permute its axes and verify:

- every label moved with its axis;
- sizes moved with their labels;
- the same `SymGroup` handles remain attached to the corresponding axes;
- independent groups remain independent;
- the output passes the normal Tensor symmetry invariant.

### 7. Story 06 same-group behavior

Retain all existing tests for:

- real symmetric transpose;
- real Hermitian transpose;
- complex Hermitian conjugation;
- antisymmetric negation;
- independent symmetry-group identity.

Add explicit tests for:

- `transpose(i, i)` returning an identical copy;
- `transpose(i, j)` and `transpose(j, i)` having the same result;
- same-group axes not causing a physical permutation in the semantic
  `transpose` path.

### 8. General permutation versus symmetry shortcut

For a symmetry-bound pair with deliberately non-symmetric test data, verify the
contractual distinction:

- `transpose(i, j)` applies the Story 06 semantic identity/conjugation/sign
  behavior;
- `permute_axes` with the equivalent raw swap performs coordinate permutation
  only.

This test ensures the two APIs do not accidentally collapse into one behavior.

### 9. Duplicate labels

Construct an `eri3`-style Tensor with two `ao` axes sharing one `SymGroup`.
Permute the axes so the two AO axes move to non-adjacent positions. Verify the
output remains constructible and `label_indices("ao")` returns the new
positions in fastest-to-slowest order.

### 10. Invalid permutations

Verify the expected exception for:

- too few indices;
- too many indices;
- a repeated index;
- an omitted index;
- an out-of-range index;
- an invalid transpose axis.

### 11. Rank edge cases

Test:

- rank-zero/default Tensor according to the documented policy;
- rank-one identity permutation;
- rank-one invalid permutation;
- a Tensor with a zero-sized dimension if that state remains supported.

### 12. `gemm` integration

Construct operands whose contraction axes are not initially in the positions
required by `gemm`. Permute them explicitly, perform the contraction, and
compare against a hand-written reference. Verify that no implicit permutation
occurs inside `gemm`.

### 13. Backend contract

Add a host backend test for the raw permutation operation, if it is exposed as
part of `TensorBackendOps`. The test must use only raw dimensions/strides and
buffers; it must not depend on labels or symmetry metadata.

### 14. Regression suite

All existing Story 02–06, Fourier, inverse-Fourier, tail, and GF2-linkage tests
must continue to pass.

## Proposed implementation steps

1. Correct and centralize the permutation convention in a small internal helper
   that validates the input and constructs output dimensions.
2. Add a host backend dense-buffer permutation/copy operation.
3. Implement `Tensor::permute_axes` using the helper and backend operation.
4. Change `Tensor::transpose(i, j)` so that:
   - `i == j` is an identity copy;
   - same-group pairs retain Story 06 semantics;
   - all other valid pairs use a two-axis physical permutation.
5. Add metadata, coordinate-mapping, aliasing, and invalid-input tests.
6. Add explicit `gemm` preparation tests.
7. Update Story 06 comments and any error messages that still claim all
   non-identical transposes are unimplemented.
8. Update Story 05's future HDF5-loading notes to reference this operation for
   axis-order adaptation, without changing the accepted data schema.

## Definition of done

- `Tensor::permute_axes` exists with the documented
  `permutation[new_axis] = old_axis` convention.
- Arbitrary valid permutations work for rank-zero through general rank tensors
  supported by the existing storage model.
- Rectangular and non-adjacent axis permutations are correct.
- `Tensor::transpose(i, j)` physically transposes distinct axes.
- Same-group `transpose(i, j)` behavior from Story 06 remains intact.
- `transpose(i, i)` is an identity deep copy.
- Tensor dimensions, labels, sizes, strides, and symmetry handles are correctly
  reordered.
- The result never aliases the source buffer.
- Validation errors are typed, actionable, and tested.
- The backend receives no labels or symmetry information.
- No implicit transposes are added to `gemm`.
- All existing tests continue to pass.
- The story leaves the codebase ready for GF2 layout adaptation and future
  basis/contraction stories.
